# Release Workflow

This document is the maintainer checklist for preparing Flight Simulator Mod Manager releases. Release preparation does not authorize a commit, tag, push, GitHub Release, or artifact upload.

## 1. Establish scope

1. Confirm the intended version and release branch.
2. Review all changes since the previous stable tag. For the first release, review the complete tracked tree.
3. Confirm that user-visible behavior agrees with `README.md`, `SPECIFICATION.md`, and `ARCHITECTURE.md`.
4. Add the newest release entry to `PATCH_NOTES.md` using `PATCH_NOTES_TEMPLATE.md`.

## 2. Check release consistency

Confirm that all current-version markers agree:

- `Config.APP_VERSION` in `src/fs24_mod_manager/config.py`;
- `version` in `pyproject.toml`;
- installer default in `installer.bat`;
- `AppVersion` in `packaging/installer.iss`;
- README current-version statement;
- newest `PATCH_NOTES.md` version heading;
- executable, installer, archive, intended Git tag, and GitHub Release version.

Search for stale development versions and unresolved release placeholders. Historical patch-note versions must not be mechanically rewritten.

## 3. Run the quality suite

From an activated development environment, run exactly the project checks documented in `AGENTS.md`:

```powershell
python -m ruff format --check .
python -m ruff check .
python -m mypy src
python -m pytest
```

Tests must use temporary synthetic package directories and must never mutate a real simulator installation. Run a hidden-window Tkinter startup smoke test on Windows as an additional release check. Record any environment-dependent check that could not be completed.

## 4. Build and inspect artifacts

After documentation and source are final:

```powershell
.\installer.bat 0.1.0
.\deploy.bat
```

For later releases, replace `0.1.0` with the selected version. `installer.bat` rebuilds the standalone executable before compiling the installer.

Inspect `dist` and verify:

- `FlightSimulatorModManager.exe` starts and reports the intended version;
- `FlightSimulatorModManager-X.Y.Z-Setup.exe` has the intended filename and installer metadata;
- `flightsimulator_mod_manager.zip` contains the intended source and release documentation;
- the ZIP excludes Git metadata, virtual environments, caches, tests, settings, logs, and generated bytecode;
- no temporary PyInstaller or Inno Setup work files remain in the repository;
- SHA-256 hashes are regenerated after the final artifact bytes are produced.

The installer is unsigned until a code-signing workflow is deliberately added. Record that limitation in the release notes rather than implying a verified publisher identity.

## 5. Final review

1. Run `git diff --check` and review the complete diff.
2. Confirm the working tree contains only intended release changes.
3. Manually test installation, Start Menu discovery, application startup, uninstall, and one enable/disable round trip against disposable test packages when practical.
4. Select a project license before public distribution or reuse.
5. Do not change source or release documentation after qualification without rerunning affected checks and rebuilding artifacts.

## 6. Publish only when requested

Only after explicit authorization:

1. Create the release commit.
2. Create the agreed tag from the exact qualified commit.
3. Push the branch and tag.
4. Create the GitHub Release using the matching `PATCH_NOTES.md` section.
5. Upload the installer, standalone executable, source archive, and checksum file.
6. Download the published assets and verify their SHA-256 hashes before announcing the release.
